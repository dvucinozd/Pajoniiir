# Risk Register

Status: current, reviewed 2026-08-16. Mitigated risks remain listed because a
future USB/audio/UI change can reintroduce them.

| Risk | Impact | Mitigation |
| --- | --- | --- |
| S3 USB host power or enumeration regresses | Blocks controller input | Enumeration and a 30-minute stability run passed on 2026-06-14; preserve raw logger diagnostics and recheck OTG port, powered hub orientation, 5 V VBUS, and shared ground after USB host changes |
| An extended Mixxx XML entry differs from actual hardware or from the official MIDI list | Wrong mapping for a non-MVP control or LED | MVP capture matched the XML exactly, so use XML addresses as implementation seeds; use the official Pioneer list as a secondary reference for LEDs/conflicts; hardware-smoke each delivered control group and record any exception in `DDJ_FLX4_MIDI_MAP.md` |
| Mixxx `Script-Binding` names are mistaken for standalone behavior | Incorrect state ownership or controls that behave differently from Mixxx | Use script-bound XML entries only for MIDI addresses; define semantic events explicitly and keep runtime deck/mixer/pad/effect state on the P4 |
| FLX4 controls or feedback generate noisy high-rate events | UART/USB MIDI queue pressure, jitter, or S3 task stack pressure | S3 translator coalesces high-rate jog/tempo/fader values; FLX4 VU feedback is low-priority/best-effort. Non-VU LED desired state is retained per `(id, deck)` across queue-full, and the USB owner retains an exact dequeued transfer across submit/completion failure with retry/drop counters. UART sequence allocation, frame build and write share one serializer. Host fault/interleaving tests pass; retain physical burst, USB-submit and reconnect LED smoke before release qualification. |
| A full S3/P4 control queue or disconnect loses the final held-control release | Scratch, Shift, Censor, Pad FX or roll remains latched after congestion/reconnect | A shared 54-slot S3/P4 reconciler retains the latest desired held level independently of queue capacity, flushes held state before continuous values, releases all observed held controls on FLX4 disconnect and replays them after P4 reboot. Capacity+1, burst, disconnect and reboot host regressions pass; retain the physical stalled-link/reconnect smoke in `STARTUP_CHECKLIST.md` before release qualification |
| Existing 7-byte control frame becomes too tight | Protocol churn | Use deck-aware ID namespace for MVP; only version frame if a real blocker appears |
| Dual MP3 decode exceeds CPU or memory budget | Audio dropouts/watchdog resets | P4 now has per-deck producer/mixer plumbing and shared output pacing; compressed audio uses a bounded LRU page cache (8 × 32 KiB per deck) instead of whole-file PSRAM, eliminating `TRACK TOO LARGE` errors and fragmentation under large files; two-deck hardware smoke shows healthy PCM ring fill and memory margins; continue measuring before adding heavier DSP/UI work |
| Dual output summing clips with loud two-deck material | Audible distortion | Channel DSP now remains wide float from pre-EQ TRIM through two-deck summing, with a single MAIN post-sum limiter, telemetry, persistent non-boosting Settings master trim, and runtime FLX4 Master Level scalar; host full-scale/multitone gates prove no pre-limiter int16 clamp, but monitor limiter/peak activity and listen for flat-top distortion on real hardware before release |
| MP3 preload/frame-index work briefly blocks audio/UI timing | Waveform or output timing spike | Active-output preload chunks are reduced, seek-table publishing uses a short lock, and audio late-warning diagnostics now report only >2x-period outliers instead of normal codec-write pacing |
| Dual output clocking, blocking I2S write or sink failure is unstable | Cue/master output can hang STOP, lose position integrity or become silent | MAIN writes now use a one-period bounded timeout, bounded short-write continuation, sink-specific counters and fail-closed output state; playback position advances only after all configured sinks accept the block, and STOP disables PCM5102 to wake the writer. Keep physical blocked-I2S/STOP/reload and dual-output smoke tests before release |
| FLAC cache I/O fault or canonical timeline wrap is mistaken for normal EOF/empty audio | Silent early track end, invalid scratch/key-lock history or position jump after long uptime | FLAC callbacks publish fault epoch/offset and replacement decoder recovery; timeline uses versioned 64-bit epochs around the 32-bit RV32 hot path with wrap regression tests, and scratch origin remains 64-bit. Retain real-FLAC USB fault injection plus seedani/long on-device timeline and scratch stress |
| P4-to-S3 monitor PCM link regresses under product load | FLX4 USB headphones may click/drop if link integrity slips after integration changes | XIAO wiring is confirmed with raw I2S data, `P4HP` magic, block CRC over header+payload, and zero steady-state deltas for sequence gaps, CRC, I2S timeouts/errors, underruns, and overruns in the 2026-07-06 five-minute soak; the 2026-07-07 product e2e re-smoke confirmed audible FLX4 headphones with P4 TX `dropped=0`; the 2026-07-09 S3 rate-match fix removed product-path ring overruns by keeping the FLX4 USB Audio packetizer aligned with the active P4 link rate after stream start; rerun a numeric soak after any I2S, task-priority, or FLX4 USB Audio scheduling change |
| ES8311/speaker amplifier path is unsafe for headphone/line output | Hardware damage if the retired local speaker path is revived casually | Current product topology uses PCM5102A RCA MAIN OUT plus FLX4 USB headphones; keep the old ES8311/speaker amplifier path out of active UI unless the schematic is rechecked and bench-measured again |
| LED feedback mapping requires script behavior not present in XML controls | FLX4 LEDs may not respond as expected | MVP Play/Cue/PFL LEDs, extended pad/loop/sync/Beat FX LEDs, reconnect resync, and official-list LED rows are verified where recorded; use XML/Pioneer list addresses as seeds, keep LED state P4-owned, and hardware-smoke each new LED group |
| FLX4 briefly shows a one-time pad sweep around the initial two-deck load sequence | Cosmetic startup indication can look like Pad FX feedback although no effect or pad action is active | Classified low priority after 2026-07-13 dual-port capture: deck routing remained correct (`0x97` D1 / `0x99` D2), playback and pad modes were unaffected, and no stack/audio fault accompanied the indication. Initial inactive pad-bank OFF bursts are suppressed and load-time Hot Cue output is diffed; do not add broader LED timing workarounds unless the symptom becomes functional or reproducible as a specific remaining MIDI packet. |
| Live Overview waveform rendering regresses UI fluidity or exhausts DSI/PSRAM scanout bandwidth | Watery motion, jitter, visible full-screen flashes or `lcd.dsi.dpi` underruns while mixing | Preserve the full two-deck scheduler budget, 49.981 Hz panel timing (`VFP=371`) and refresh-done-driven firmware `ui_update()` cadence accepted in the 2026-07-17 132-second development smoke and more-than-71-second exact signed-candidate re-smoke. Do not restore one-deck alternation or the ineffective DW-GDMA QoS override. Rerun host scheduler tests, a P4 build and a dual-play COM15 smoke after panel timing, framebuffer, PPA, PSRAM/cache or Overview renderer changes; require zero DSI underruns and operator confirmation of fluid, flash-free motion |
| Dense Overview chrome overlaps controls on the 800x480 P4 screen | Play/Cue, VU, title, or effect data becomes hard to read or touch | Keep compact fixed-size lanes for D1/D2 badges, VU meters, transport controls, title strip, and Beat FX rail; preserve static layout guards and do a hardware visual review after every Overview polish batch |
| Controller task performs heavy UI/library work | Stack overflow or UI-context bugs when hardware buttons navigate Library/Overview | 2026-06-25 smoke found a `deck` task stack protection fault on Browse; `deck` task stack is now 8192 bytes as a stabilizing fix. Since 2026-07-26 the deck task only enqueues bounded browse/load commands and `ui_update()` drains at most eight per frame on the LVGL task. The Library UI table is now paginated (one 8-row page with PREV/NEXT, max 40 live LVGL cells) so large catalogs no longer create unbounded LVGL widget counts. Preserve the host ownership guards and do not reintroduce direct controller-task UI/library calls |
| P4 local build remains in debug optimization | Reduced UI/audio headroom and waveform jitter | `sdkconfig.defaults` now selects performance optimization and disables LVGL examples/demos. Regenerate or align ignored local `sdkconfig` files before flashing |
| Upstream code changes are mixed with DDJ-specific changes without notes | Hard to reason about port | Keep DDJ docs explicit and update development plan after each phase |
| A retained or linked-worktree branch is merged or deleted without a reachability audit | Reintroduces stale code or discards unique work | A 2026-07-20 audit closed the last outstanding branch: `codex/phase-8-implementation` was confirmed superseded by `master`, its unique GPIO48 WS2812 RGB status-LED policy engine was archived under tag `attic/phase-8-status-led-policy`, and its branch/worktree were removed. A 2026-07-26 follow-up confirmed five remote maintenance branches and two stale local branches were already ancestors of `master` with 0 unique commits before removing them; only `master` remains local + remote. Keep the discipline for future branches: before merge/delete/prune, run `git branch --no-merged master`, inspect worktree ownership and commit reachability, and archive any unique work under an `attic/*` tag rather than deleting it |
| OTA signing key is lost, copied or cannot be rotated | Unauthorized firmware could be signed, or legitimate future OTA releases could become impossible without wired access | Devices verify ECDSA P-256 bundles with committed key ID `rel-001`; an offline USB backup was confirmed during signed-path hardware acceptance on 2026-07-14. Keep both copies access-controlled and move production signing to encrypted or hardware-backed storage with a documented multi-key/rotation migration |
| An OTA transfer result is mistaken for firmware validity | A successful upload or top-level `state=idle` could be misreported as complete functional acceptance | Distinguish transport (`HTTP 200`, local OTA transfer state) from boot/image validity and application behavior. A pending S3 image now also requires critical-task liveness plus an exact P4 echo of a fresh boot challenge before mark-valid; timeout restarts without confirmation. After P4 reboot, use `/api/status` plus firmware/version/slot data; for S3, use the P4 nested firmware report and its per-image `state`. The 2026-07-16 `RC1-131-gc391e306` deployment passed signature, transfer, reboot and version agreement, but not the deferred functional smoke. The 2026-07-17 `RC1-133-gbd5e43ce` candidate passed signature/package checks and exact-payload COM15 display smoke, but its wired factory flash does not prove a new HTTP OTA transfer or slot transition |
| Current RC2 source and installed candidates have not received one complete functional hardware pass | A Phase 20, controller-profile, UI or integration regression could remain hidden although focused feature paths pass | Keep `RC1-123-g587cd7a1` documented as the latest fully accepted known-good/reinstall baseline. The signed and packaged RC2 applications installed successfully through OTA on both boards on 2026-08-02. Complete IDF6 boot chains then passed, including the P4 SDMMC fix. A later focused smoke passed display/touch/Settings/Library, FLX4 MIDI/LED, MAIN/cue and real-MP3 playback. It did not cover WAV/FLAC (the PDB rows referenced absent files), sustained USB/cache counters, recovery, guarded web/profile/OTA mutations, UART fault injection or long DSP/Beat-FX stress. Run those remaining rows before enclosure or production use |
| A local AP client forges, malforms or deliberately stalls web mutations | Playback/controller/OTA state could change unexpectedly, or the single HTTP task could be held unavailable | P4 and S3 mutation handlers require the fixed device Host and explicit control header, enforce POST and bounded parsing, and validate uploads before activation. S3 additionally requires the current six-digit operator code, locks it after five failures, expires it after ten minutes and shuts the AP down after fifteen minutes. S3 rejects oversized OTA bodies early and enforces a 180 s total plus 10 s/4096 B progress budget; started OTA handles abort on failure. Recheck authorization and slow-client recovery from a phone during hardware acceptance; the P4 AP remains a local trusted-service surface rather than an Internet-facing API. |
| The service AP's WPA2 password is a published constant | Anyone within radio range who has read the repository or the developer guide can join the AP and drive every guarded mutation — transport control, track load, recording start/stop, controller-profile upload — so a set can be disrupted by a bystander | **Accepted, not mitigated (2026-07-29 decision).** `WIFI_LINK_PASSWORD` is `"Pajoniiir"`, defined in a committed header and printed in `firmware/main-deck-p4/CLAUDE.md`, so WPA2 provides no real access control. What this does *not* expose: the CSRF defence is sound (Host allow-list plus a required `X-DDJ-Control` header on all eight POST endpoints, no CORS headers and no OPTIONS handler, so cross-origin mutation fails at preflight), and `/api/ota/p4` verifies an ECDSA P-256 manifest before erasing flash, so firmware cannot be forged — the exposure is disruption, not code execution. The AP is also off by default and user-toggled. Revisit before any use where the operator is not the only person in range, or if the device is ever shipped to third parties; the contained fix is a per-device random PSK generated at first boot, persisted in NVS and shown on the Settings screen, which needs no protocol or web-UI change but does invalidate saved client credentials |
| The S3 Debug AP WPA2 password is a published constant | A nearby client can associate with the bench AP and attempt its OTA mutation | **Software mitigated 2026-08-16.** Association alone no longer authorizes `POST /api/ota/s3`: each ON edge generates a random six-digit maintenance code shown on the authoritative P4 Settings UI, valid for ten minutes and locked after five failures. OFF clears the code, ON regenerates it, and a fifteen-minute timer shuts down the AP. Signed-manifest verification remains the firmware-authenticity boundary. Hardware acceptance must verify unauthenticated/wrong/expired/locked requests cannot begin flash and that supervised signed rollback still succeeds. |
| Final enclosure changes power, temperature or RF behavior | Audio instability, brownout, USB disconnect or inaccessible service AP after USB ports become hard to reach | Run closed-enclosure dual-deck/audio soak, measure rail/temperature margins, verify AP reachability and retain a wired recovery/service path before sealing |
| Master Tempo quality or CPU cost degrades under simultaneous demanding material | Artifacts or deadline misses with key lock active on both decks | Basic hardware behavior is accepted. The 2026-07-16 DSP pass removes repeated reference-window reads, rejects losing correlation candidates early, avoids stable filter recomputation and prepares mixer controls once per block. A deterministic five-minute simultaneous dual-deck host soak passed 2026-07-26 with zero drift, detected clicks or clipping, but host runtime does not measure P4 CPU/I2S deadlines or listening quality; retain the long on-device two-deck acceptance before declaring production DSP quality |
| Focused Beat FX acceptance does not cover every transition/timing edge | Detailed target routing, live beat-size changes or shared Echo/Delay tails may still regress on the actual MAIN/cue path | Filter/Echo/Flanger/Delay sound and headroom have recorded hardware acceptance as of 2026-07-24. Retain the remaining E1A matrix on CH1, CH2 and `1&2`, including Level/Depth, beat-size changes and mode transitions. Delay samples effective BPM only when Beat FX state is applied, accepts 40–300 BPM (otherwise 120 BPM), caps at 1000 ms and derives combined-target timing from Deck 1. Later tempo/Beat Sync/track changes do not automatically retime the line. Listen for unacceptable clicks, the previous-period Delay tail, ~2 s Echo tail and clean shared-line Echo↔Delay reset |
| Only the FLX4 controller profile is end-to-end verified | Profile schema defects may remain hidden for other controller layouts | Validate one non-FLX4 controller including input, LED output, reconnect and profile fallback before advertising generic compatibility |
| A remote controller-profile overwrite is corrupt or loses power mid-write | The S3 could lose its active MIDI/LED mapping after the enclosure makes SD access difficult | P4 accepts only bounded CRC-valid S3CP v2 blobs, requires strict non-traversable IDs and explicit overwrite, serializes install against transfer, writes/syncs a same-directory staging file, preserves the previous target as a backup, recovers interrupted swaps during scan and reactivates only after a successful rescan; retain the built-in FLX4 fallback and hardware-test interruption before closing the feature |
| The P4 web layer stops serving while the board still looks healthy | Loss of `/api/ota/p4`, the only remote recovery path, from a device that answers ping and shows a working AP | Two distinct traps, both hardware-observed on 2026-07-21. (1) `max_uri_handlers` too low: one failed `register_uri_or_stop()` calls `httpd_stop()` and takes every endpoint down at boot; the limit now sits at 24, above the registered count, and must stay there. (2) Socket exhaustion: `max_open_sockets` is 5 and the controller page holds keep-alive sockets while polling `/api/status` every 250 ms, so one busy browser filled the pool and the server refused all new clients until `lru_purge_enable = true` was set in `RC1-175-ge40b7225` (verified: 8 concurrent requests all served). Distinguish them by signature — the URI trap kills the server for everyone from boot, while exhaustion still serves the already-connected client and clears itself about 20 s after it disconnects. Do not reach for a wired COM15 recovery on the exhaustion signature. Re-check both after adding endpoints or changing the page's polling. |
| A weak bench supply is mistaken for a Wi-Fi or firmware reboot | Time is spent debugging the wrong subsystem and an unstable supply can interrupt playback or OTA | The recurring reboot was closed on 2026-07-24 by three consecutive `reset=BROWNOUT` records and stopped after replacing the power supply; the journal contains 18 historical brownouts. Wi-Fi bring-up still emits the synced `WIFI_ENABLE_REQUESTED` breadcrumb plus `WIFI_STARTED`/`WIFI_FAILED` heap and stack data, so retain those diagnostics. Treat any recurrence by reset reason first and verify the supply before attributing it to ESP-Hosted or the Settings path |
| microSD stalls for hundreds of milliseconds at a time, below FATFS | The recorder drops seconds of audio and playback stutters; the card sits behind an enclosure that must be opened to change it | The recorder is shelved and compiled out by default through `CONFIG_AUDIO_RECORDER_ENABLED=n`. Its safety was hardened: STOP closes the producer gate and waits for in-flight writers before drain; finalise uses a transactional `patch`→`sync`→`close`→`publish` pipeline that propagates every durability failure and refuses to rename a partial `.part` file. A single write on the original card blocked ~370 ms in bursts that drained the 2.95 s ring; firmware-side gate, journal and header-patch contributions were eliminated, and PSRAM staging was worse. A replacement card looked better for five minutes but the required 25-minute soak was intentionally not completed, so it is not accepted evidence. Do not enlarge the ring or resume recorder work unless product scope explicitly reopens it; then qualify the card with `tools/sd_card_latency_probe.ps1` and require a full 25-minute soak before drawing conclusions |
| ESP-IDF 6.0.2 migration introduces hardware regressions | Display, touch, USB MSC, audio, Wi-Fi or OTA may behave differently under the new IDF | **The migration is on `master` with hardware acceptance in progress.** The software gates all pass — clean S3 and P4 builds on 6.0.2, both host suites and the UI simulator screenshot gate — but a green CI run is evidence about code, not silicon. The 2026-08-02 full flashes proved both IDF6 boot chains and exposed then closed the P4 ESP-Hosted/microSD SDMMC-controller ownership defect. A focused follow-up passed display/touch/Library, FLX4 MIDI/UAC/LED, PCM5102A, monitor audio and real MP3. USB cold/reboot/disconnect recovery, real WAV/FLAC, sustained BNA and locked-read counters, ESP-Hosted AP/OTA and migrated rollback coverage remain in `docs/migration/ESP_IDF_6_0_2_MIGRATION.md`. **RC2 is therefore not release-qualified** |
| Rekordbox PDB row exists while the referenced audio file is absent | A format can be misdiagnosed as unsupported because Library shows a track that must fail at `fopen()` | Before codec acceptance, verify the referenced `/Contents/...` file physically exists on the USB and capture the exact load error. The 2026-08-02 `L:` audit found 68 MP3 files, zero WAV/FLAC files and two WAV PDB paths with no corresponding files. Re-export fixtures through Rekordbox instead of treating `ESP_ERR_NOT_FOUND` as a decoder failure |
